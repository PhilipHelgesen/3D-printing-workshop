# Rows should part to show where the drop lands

Status: done — shipped in 3538e29
Category: bug

Reported: 2026-08-26

> Where I want to place it, other parts should move out of the way, so it's
> seamless and dynamic. Now it's hard, sharp, and is placed above other parts.
> They need to move out of the way so I can see where I'm placing it.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** During a list drag, the rows around the landing spot never move; a
dashed indicator is painted over the seam instead. The list should part to make
real room for the held item.

**Current behavior:**
The list view's drag layer is built on `@dnd-kit/core`. Two things were traded
away to stop a re-measure feedback loop, and both are visible as this bug:

1. The dragged row stays in the list, dimmed to 30% opacity. It was agreed it
   would collapse to nothing, leaving no ghost behind.
2. The landing spot is marked by an absolutely-positioned, dashed, tinted
   rectangle drawn *over* the boundary between two rows. It takes no space, so
   the rows on either side of it do not move, and the indicator overlaps the row
   below it — the "hard, sharp, placed above other parts" the report names.

The cause of the trade: dnd-kit decides what the pointer is over using
rectangles. With continuous measuring enabled, a gap that really opens changes
the layout, which triggers a re-measure, which re-runs the layout — the app
white-screened with "Maximum update depth exceeded" on every drag. Measuring was
therefore returned to its default (measure once, before the drag starts) and the
gap was made layout-neutral.

**Desired behavior:**
The key is that the two goals are not in conflict once nothing about the
*layout* changes. Collision detection should keep running against the rectangles
measured before the drag; the parting should be done with CSS transforms, which
move rows visually without moving them in the layout.

- The source row leaves the list: it collapses to nothing, with no dimmed ghost.
- A space the height of the held item opens at the landing spot, and the rows
  below slide down to make it. Both the collapse and the opening are animated,
  not instant.
- The space follows the pointer as the aim changes, sliding rather than jumping.
- Dropping a part onto an assembly opens the space *inside* the panel, at the
  member position it will take.
- The dashed overlay rectangle is deleted. The space itself is the indicator.
- No white-screen: dragging across a list of ~30 rows, in and out of assemblies,
  never throws "Maximum update depth exceeded".

**Key interfaces:**
- The pure write side is finished and correct — `reorderPart(state, id,
  targetId, before)` and `reorderGroup(state, groupId, targetId, before)` in
  `workshop.ts`, asserted in `derive.check.ts`. This issue changes nothing about
  them and adds no new state to `types.ts`.
- The drag layer's aim type (anchor row or panel, `before`, and whether the drop
  joins an assembly) already carries everything the parting needs: from the aim
  and the visible row order, each row's shift is one of `0` or `±heldHeight`.
- dnd-kit's measuring configuration must stay at its default (before-drag).
  `MeasuringStrategy.Always` / `.WhileDragging` are what caused the crash. A
  transform-based parting is compatible with before-drag rects *because* it
  doesn't touch layout — the pre-drag rectangles stay the right ones to hit-test
  against.
- Prefer transform offsets over `@dnd-kit/sortable`; that would be a new
  dependency and needs the maintainer's approval first.

**Acceptance criteria:**
- [ ] Picking up a row removes it from the list with no ghost left in place.
- [ ] A space the height of the held item opens where the drop will land, and
      the rows below it are pushed down by exactly that height.
- [ ] Moving the pointer between landing spots slides the space; it does not
      appear and disappear.
- [ ] No dashed or tinted placeholder rectangle is drawn over any row.
- [ ] Dropping onto an assembly opens the space inside the panel.
- [ ] A drag across a full build (~30 rows), in and out of assemblies, produces
      no console error and no white screen.
- [ ] `npm run check` and `npm run build` pass.

**Out of scope:**
- The drop rules themselves — what joins, what unlinks, what reorders — are
  settled and correct. Don't change `reorderPart`/`reorderGroup` or the aim
  rules.
- The flying item's appearance and its 150ms width animation are settled.
- Tiles view. Drag is list-only.
- Keyboard dragging.
- Adding a dependency without asking.
